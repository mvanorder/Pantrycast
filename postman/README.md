# Postman collection

`pantrycast.postman_collection.json` covers every endpoint currently implemented in the
backend — health checks, order-history CSV upload, and the register/verify-email/login/refresh/
logout/password-reset auth loop from [`docs/design/uac-design.md`](../docs/design/uac-design.md)
§1. It's
generated by hand today, kept in sync with [`docs/api/openapi.json`](../docs/api/README.md)
manually — importing the raw schema instead (Postman's own "Import" → paste the OpenAPI URL) is
the fallback if this drifts.

## Setup

1. Import `pantrycast.postman_collection.json` into Postman (File → Import).
2. Import `local.postman_environment.json` too, and select it as the active environment (top-right
   environment picker) — it just points `base_url` at `http://localhost:8000`. Duplicate it and
   change `base_url` for staging/prod.
3. Have the backend running against it: `docker compose -f docker-compose.yml -f
   docker-compose.dev.yml up -d` from the repo root, or `uvicorn app.main:app --reload` from
   `backend/` with the venv active.

## Running it

Open the **Auth** folder and run the requests top to bottom (or use Postman's "Run collection" on
just that folder):

1. **Register a new account** — its pre-request script generates a random `test_email` and a
   fixed `test_password` collection variable *the first time only* (skipped if they're already
   set, so re-running the folder doesn't fail by trying to reuse a real account's email — it'll
   just log back into the same one). To register a genuinely new account, clear `test_email` /
   `test_password` on the collection's Variables tab first. This also schedules a verification
   email, whose token the next request needs.
2. **Verify email address** — needs manual setup, so it isn't part of an automatic top-to-bottom
   run: the raw token is never in the register response, only in the email itself, or — with
   `EMAIL_BACKEND=console` (the local-dev default) — in the backend server logs, as the `token=`
   query param on the emailed `.../verify-email` link. Copy that value into the
   `verification_token` collection variable before running this request. Account use itself
   doesn't depend on this — login/logout below work regardless of whether it's been run.
3. **Log in** — stores `access_token`/`refresh_token` as collection variables from the response.
4. **Refresh the token pair** — rotates both, using (and updating) the same variables.
5. **Log out (this session)** / **Log out all sessions** — use the bearer token set above; either
   will make the stored `refresh_token` stop working (try Refresh again afterward to see the 401).
6. **Request a password reset** / **Confirm password reset** — a second manual pair, the same
   shape as step 2: the first always 204s (anti-enumeration) and schedules the reset email; the
   raw token is only ever in that email, or — with `EMAIL_BACKEND=console` — in the backend server
   logs, as the `token=` query param on the emailed `.../reset-password` link. Copy that into the
   `password_reset_token` collection variable before running the second request. Confirming also
   revokes every refresh token on the account (like Log out all sessions), and updates the
   collection's `test_password` to the new value it sends — so **Log in** works again afterward
   without editing anything by hand.

**Users → Get current user** and both logout requests read the `access_token` collection variable
via a bearer-auth entry on the request — run **Log in** (or **Refresh**) at least once first, or
they'll 401.

**Health** and **Orders → Upload an order-history CSV** don't need auth and can be run any time;
the upload request needs a `.csv` file selected manually in its Body tab (Postman can't embed a
file path portably across machines).

## Notes

- Every request that expects a specific status also runs a `pm.test(...)` assertion, so
  "Run collection" gives a pass/fail summary, not just response bodies to eyeball.
- Tokens/test credentials live in **collection variables**, not the environment, since they're
  runtime state produced by the requests themselves, not per-environment config.
